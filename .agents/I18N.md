# i18n Task Instructions

Working instructions for translating the patcher UI into German. Read this file
in full before touching any code, then execute only the chunk you were asked to.

## Goal

The UI must be available in English and German, switchable live at runtime.
**Log and console output stays English in every language.** The architecture is
already in place — your job is to move hardcoded strings into the locale files
and annotate the markup.

## The architecture (already built, do not redesign)

- `src/i18n/index.js` — engine. Exports `t(key, vars)`, `tPlural(key, n, vars)`,
  `setLocale`, `getLocale`, `getLocales`, `onLocaleChange`, `applyTranslations`.
- `src/i18n/registry.js` — the list of languages. Adding a language means adding
  one locale file and one line here. Never hardcode `<option>` markup anywhere.
- `src/i18n/locales/en.js` — canonical, must be complete.
- `src/i18n/locales/de.js` — same key shape.
- `src/main.js` already imports `t`, `tPlural`, `getLocale`, `getLocales`,
  `setLocale` and calls `await initI18n(appSettings.language)` on startup.

Locale files are nested objects; lookups use flat dot-paths (`flatten()` bridges
the two). So this:

```js
export default { tabPatcher: { heading: 'Select Patch Mode' } };
```

is reached as `t('tabPatcher.heading')`.

## THE RULE: translate, or leave English?

> A string is UI text and gets translated — **unless it is rendered inside a
> console/log panel**, in which case it stays English, no matter which API put
> it there.

Apply in this order:

1. A literal argument to `log(...)`, `logTo(...)`, `gLog(...)`, `bLog(...)`, or
   anything arriving through the `app-log` Tauri event (`src/main.js:7-17`)
   → **leave English. Do not wrap in `t()`.**
2. Static HTML text whose nearest ancestor is `#console-logs`, `#genpatch-logs`,
   `#build-logs`, or `.console-body` → **leave English, add no `data-i18n`.**
   This covers, specifically:
   - `<div class="log-line system">Waiting for process start...</div>`
   - `<div class="log-line system">Ready to create patches...</div>`
   - `<div class="log-line system">Build output will appear here...</div>`
   - the hardcoded `'Console cleared. Waiting for process...'` inside
     `clearConsole()` in `src/main.js`
3. `console.log` / `console.warn` / `console.error` → **leave English**
   (developer diagnostics).
4. Everything else the user can see → **translate.** This explicitly *includes*
   the console *chrome*: the `Execution Output` heading, the copy/clear button
   tooltips, the resize-grip tooltip, and the Small/Medium/Large/Tall size
   buttons. Only the log *lines* stay English, not the furniture around them.
5. Never translate proper nouns: `ACTIONS & STUFF`, `RTX PATCHER`, `A&S`, `RTX`.
   Pure data (file paths, version numbers, slugs, byte counts) is never a key —
   it goes through interpolation as a `{var}`.

Rust-side strings (`emit_log()` in `src-tauri/`) are **out of scope entirely**.
Do not open those files.

## Key naming

`<namespace>.<subarea?>.<element>[.<role>]`

Namespaces follow the tab ids, so a chunk's markup diff maps 1:1 onto its locale
diff: `common`, `sidebar`, `nav`, `tabPatcher`, `tabCleaner`, `tabRtxSettings`,
`tabUtils.<pack|extract|genpatch|brarchive>`, `tabSupport`, `tabRelease`,
`tabAppSettings`, `modal`.

Examples: `nav.patcher`, `sidebar.advancedMode`, `modal.notificationTitle`,
`tabAppSettings.defaultPatcherMode.label`, `common.cancel`.

**Before adding a key, grep `en.js` for the exact English string.** If it is
already there, reuse that key. Anything appearing in more than one tab belongs
under `common.*`. Duplicate keys for the same phrase drift apart in German and
are the main source of inconsistency here.

## HTML annotation

Four attributes: `data-i18n` (replaces `textContent`), `data-i18n-placeholder`,
`data-i18n-title`, `data-i18n-alt`.

**Leave the English text in the markup.** You are adding an attribute, not
rewriting a node. The English text is what you copy into `en.js`, and it keeps
the page readable if the engine ever fails to run.

**`data-i18n` goes only on elements whose children are pure text.** On a parent
with element children, `textContent =` deletes those children silently, with no
error. The icon simply disappears at runtime.

```html
<!-- WRONG: this deletes the ⚡ span at runtime -->
<button class="nav-tab" data-i18n="nav.patcher">
  <span class="tab-icon">⚡</span> <span class="tab-text">Patcher</span>
</button>

<!-- RIGHT -->
<button class="nav-tab">
  <span class="tab-icon">⚡</span>
  <span class="tab-text" data-i18n="nav.patcher">Patcher</span>
</button>
```

An emoji sitting in the **same text node** with no wrapping span is not mixed
content — annotate the element directly and keep the emoji inside the translated
string on both sides:

```html
<h2 data-i18n="tabAppSettings.title">⚙️ Application Settings</h2>
```

Do not split such an emoji into a new span. That is a structural change, and
structural changes are out of scope.

**Invariant:** the value of `en.<key>` must be **character-for-character
identical** to the text you annotated — same emoji, same punctuation, same
spacing, same `…` vs `...`. English is live output, not just a translation
source, so a retyped string silently changes the English UI. Copy, never retype.

## JS strings

```js
// before
updateStatus("Preparing Patch File", `Downloading ${patchKey} patch (${totalMb} MB)...`, '⬇️');
// after
updateStatus(
  t('tabPatcher.status.preparingTitle'),
  t('tabPatcher.status.downloading', { patch: patchKey, total: totalMb }),
  '⬇️'
);
```

- Every `${expr}` becomes a **named** `{placeholder}` describing the value, not
  a mangled copy of the expression: `${(freed / 1048576).toFixed(1)}` → `{mb}`.
- Singular/plural uses `tPlural`, with `.one` and `.other` sub-keys and a
  pre-filled `{count}`:

```js
total.innerText = tPlural('tabPatcher.cache.summary', n, { mb });
```
```js
cache: { summary: {
  one: '{count} patch downloaded · {mb} MB total',
  other: '{count} patches downloaded · {mb} MB total',
} }
```

- No branching logic inside locale values. No HTML inside locale values. All
  conditionals stay in JS.
- A multi-paragraph string with `\n\n` stays **one** key, newlines included.
  Do not split it, unless the paragraphs are genuinely reused elsewhere.

## German style

- Address the user with **"du"**, matching the app's informal tone.
- Keep established English technical terms that the target audience uses:
  *Patch*, *Patcher*, *Pack*, *Mod*, *Shader*, *Update*, *Log*, *Backup*.
  Translate the surrounding sentence, not the jargon.
- Keep every emoji, every leading/trailing space, and every `…`/`...` exactly as
  in English. Only the words change.
- German runs 20-30% longer than English. Keep button and tab labels tight —
  a nav label that wraps breaks the sidebar layout.

## Guardrails — run these before you report done

```sh
node --check src/main.js          # a syntax error kills the whole app
node scripts/check-locales.mjs    # en and de key sets must match exactly
```

Then confirm by hand:

- `grep -n "log(\|logTo(\|console\." src/main.js` — none of these lines may
  appear in your diff.
- The three console placeholder lines in `index.html` are untouched.
- Tag counts inside the section you edited are unchanged
  (`grep -c "<span" src/index.html` before vs after).
- Every string containing `\n` still contains those newlines after translation
  (`#motd-title` relies on `white-space: pre-line`).

## Scope discipline

- Touch **only** the files and line ranges of the chunk you were given.
- **Never run `git commit`, `git push`, `git checkout`, or `git reset`.**
  Leave your changes in the working tree. They get reviewed before they land.
- Never reformat, reorder, or "clean up" code you were not asked to change.
  A noisy diff cannot be reviewed against the character-identical invariant.
- If a string is ambiguous under THE RULE, leave it English and list it in your
  final report rather than guessing.
